### ReMa MCP tests

`src-tauri/src/rema_mcp/tests.rs` drives the tools through ReMa's real MCP
client (`rmcp` 3.4.1, protocol 2026-07-28) against the in-process server,
with a local fixture site standing in for SearXNG, the Greenhouse Job Board
API and employer career pages (including `robots.txt`, a closed posting, a
non-posting page, a LinkedIn link and a page that tries to instruct the
model).

| Test | Checks |
|---|---|
| `serves_five_tools_over_mcp_and_finds_jobs_end_to_end` | Five tools, output schemas, read-only annotations, negotiated protocol; a search returns the Greenhouse job and the employer page with provenance and real posting dates; the other city is filtered out; the closed posting and non-postings are counted; LinkedIn and the `robots.txt`-disallowed page stay unresolved and are never requested; payload ≤ 32 KiB. |
| `cached_searches_cursors_and_truthful_refresh` | Snapshot reuse with no new requests, cursor paging, cursor bound to its query (`INVALID_INPUT`), `refresh: true` really searches again. |
| `reads_jobs_in_detail_one_or_many` | `get_job` by ID (recent check reused) and by URL with `refresh` (source read again); 12,000-character description parts with a continuation cursor; typed errors (`JOB_NOT_FOUND`, `INVALID_INPUT`, `BLOCKED_BY_SOURCE_POLICY` for a LinkedIn URL, the cloud metadata address refused); `get_jobs` keeps order, reports per-item errors and caps items at 5,000 characters. |
| `similar_jobs_and_source_status` | `search_similar_jobs` from a stored job excludes the seed; `source_status` reports the backend kind and 20 s deadline, each source's acquisition mode and last success, and no key material. |
| `an_unreachable_source_is_tried_once_and_reported_once` | With the Greenhouse API unreachable, each job is tried once (the employer-posting lookup does not read it again) and the failure is reported as one `SOURCE_UNAVAILABLE` warning for the source. Fails on the code before the fix. |
| `without_a_search_backend_search_fails_but_urls_still_work` | `SEARCH_BACKEND_UNAVAILABLE`; `get_job` still works. |
| `enabled_by_default_and_the_saved_choice_survives_restarts` | First launch writes `true`; a restart over the same database keeps `false`; nothing re-enables it. |
| `disabling_blocks_calls_and_cancels_running_work_but_keeps_saved_jobs` | A running search is cancelled (`CANCELLED`) well before it would have finished; new calls are rejected by the server; saved jobs remain; turning it on again restores calls. |
| `never_reads_profile_data` | The engine, server, host, store and adapters have no path to Profile storage. |

Unit tests cover the source registry and URL safety (`sources.rs`), the
fetcher (private addresses refused at connect time, redirects, size limit,
one retry, `robots.txt`), each adapter (Greenhouse, Lever, Ashby, Personio

## 4. Measurements

`cargo test --lib measure_cold_and_warm_calls -- --ignored --nocapture`,
three runs. Debug (unoptimized) test build against the loopback fixture
site, so there is **no network latency**. These figures show ReMa MCP's own
overhead, not live search times.

| Step | Time (3 runs) | Payload |
|---|---|---|
| Open an MCP session (`server/discover`, `tools/list`) | 53–59 ms | |
| `search_jobs`, cold: 7 search requests (6 discovery + 1 employer-posting lookup), API and page reads, filtering, storing | 108–135 ms | 4,107 bytes |
| `search_jobs`, same search again (10-minute snapshot) | 2.7–6.0 ms | 4,106 bytes |
| `get_job` with `refresh: true` (reads the Greenhouse fixture API) | 19–24 ms | 15,028 bytes (a 12,000-character description part) |
| `get_job` again (recent check reused) | 3.5–7.4 ms | |

Payload limits enforced by tests:
- search output ≤ 32 KiB (`serves_five_tools_over_mcp_and_finds_jobs_end_to_end`);
- description parts of 12,000 characters;
- batch items ≤ 5,000 characters (`reads_jobs_in_detail_one_or_many`).

Cancellation: with each search request taking 3 s, disabling ReMa MCP
during a search returned `CANCELLED` in under 2.5 s, measured from the
start of the call (`disabling_blocks_calls_and_cancels_running_work_but_keeps_saved_jobs`).

Live sample size: **0**. No public job platform, ATS API or search engine
was reachable from this environment, so there is no live precision, recall
or latency figure.

## 5. Defects found and fixed during validation

- **Stale Settings card.** After the switch was used, the card kept showing
  that action's result even when a newer status arrived from the backend,
  for example after the search service changed. The newest backend status
  now wins (card test "shows the newest status from the backend after an
  action").
- **Search-service change not signalled.** Saving or removing the search
  service did not signal the card to refresh. It now emits the MCP-changed
  event.
- **Duplicate page read.** The employer-posting lookup re-read a page the
  first pass had already failed on (see §3).
- **Dev variable name in release.** The release binary contained the name
  of a debug-only variable. Its value was already ignored in release; the
  switch is now compiled only into debug builds.
- **Test support stalled workers.** The mock HTTP server ran blocking
  handlers on async worker threads. That made the cancellation test
  timing-sensitive under load (one failure in a full run). Handlers now run
  on the blocking pool, and the test allows 2.5 s against a 3 s request.

## 6. Remaining limitations

- **Live sources unverified.** The Greenhouse, Lever, Ashby and Personio
  endpoints and response fields follow the vendors' public documentation as
  known at implementation time. They are tested only against fixtures.
  Verify them against the live services before release. EU-hosted
  Greenhouse boards are read as employer pages because the EU API host was
  not verified.
- **Discovery depends on the user's setup.** Search needs one of:
  - a configured search service (Brave, Tavily, SearXNG), or
  - a chat model with provider-hosted web search.

  Otherwise `search_jobs` returns `SEARCH_BACKEND_UNAVAILABLE`. Coverage is
  whatever those indexes return; LinkedIn, XING and regional boards are
  links only.
- **Provider-hosted discovery deadline is 90 s**, not 20 s: one model turn
  with searches commonly takes longer. `source_status` reports it.
- **Scheduled tasks** keep the enforced job-search workflow from the
  previous release. ReMa MCP tools are offered in chats, not inside
  scheduled task runs.
- **Enforced job-search path unchanged.** Messages detected as job searches
  still go through the existing retrieval workflow; ReMa MCP tools are
  offered for everything else, including job-description questions and
  comparisons.
- **Models without tool support** get no ReMa MCP tools. Once a model
  rejects tools, it is not offered them again for the rest of the session.
- **Protection is limited.** The implementation is compiled into the
  stripped release binary, with no JavaScript job-search logic and no
  source maps in the release frontend. Locally distributed binaries can
  still be inspected or reverse-engineered.
